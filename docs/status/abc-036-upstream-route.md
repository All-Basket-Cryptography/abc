## Verification scope

Use the original C implementation and a C source semantics that models the pinned 32-bit unsigned operations, byte order, pointer bounds, and declared build settings. The first target should be the compression operation on exactly 64 input bytes and eight initial words. Compare its updated words against `Abc.Spec.Sha256`'s round, schedule, and feed-forward semantics. Relate the C circular 16-word message schedule to each applicable window of the Lean model's 64-word schedule. Then extend the relation to padding, serialized outputs, and the upstream streaming C API's error behavior. [Pinned C implementation](https://raw.githubusercontent.com/python/cpython/v3.14.2/Modules/_hacl/Hacl_Hash_SHA2.c)

HACL* separately publishes its F* source verification and KreMLin extraction route. A bridge through it would require the exact verified F* revision, checked C extraction or source correspondence, and a checked relation to the shared Lean specification. The CPython binding consumes the C API and discards its overflow status in `update_256`. Its successful bounded-message inputs are a separate claim from the ABC API's overflow rejection. The same distinction applies to build and target-binary evidence.
